# WebToMobile v0.2.0 Implementation Brief

> *Audience: maintainers. A work brief for the v0.2.0 changes — not needed to use the plugin.*

## Context

WebToMobile is a **plugin/skills helper for AI coding agents** that converts websites into Expo React Native mobile apps. It audits, plans, implements, and verifies — nothing else.

This brief covers 6 targeted improvements for v0.2.0. All changes are optimizations and capability improvements within the existing scope. Do not add new commands, new skills, or new workflows. Do not change the intended usage.

**Maintenance rule:** only change what improves install clarity, migration quality, agent accuracy, token efficiency, or validation trust.

**Validator:** run `node tests/validate-structure.mjs` after every change. It must pass before committing.

**Skill word limit:** every `skills/*/SKILL.md` must stay under 500 words.

## Improvement 1 — Next.js App Router Detection

**File:** `scripts/web-repo-audit.mjs`

**Problem:** The audit detects `next` in dependencies and outputs `"Next.js"` in the frameworks array, but it cannot distinguish between Pages Router and App Router. These have very different migration paths — server components, route groups `(group)/`, and server actions need different handling.

**What to add:**

After the frameworks array is built, detect the router type:

```js
// Detect Next.js router type — App Router vs Pages Router
let nextjsRouter = null;
if (allDeps["next"]) {
  const hasAppDir =
    existsSync(join(root, "app")) ||
    existsSync(join(root, "src/app"));
  const hasPagesDir =
    existsSync(join(root, "pages")) ||
    existsSync(join(root, "src/pages"));
  nextjsRouter = hasAppDir && !hasPagesDir
    ? "app-router"
    : hasPagesDir && !hasAppDir
      ? "pages-router"
      : hasAppDir && hasPagesDir
        ? "app-and-pages-mixed"
        : "unknown";
}
```

Add `nextjsRouter` to the JSON output (it will be `null` for non-Next.js projects).

Also add server component detection to `serverSignals` — scan for `"use client"` directives (their absence in files under `app/` confirms server components are in use):

```js
["use-client-directive", /["']use client["']/g],
```

Add to `serverPatterns` array alongside the existing entries.

**Output field to add:** `nextjsRouter` (string or null).

**Validator update:** add assertion:
```js
assert(Object.prototype.hasOwnProperty.call(fixtureAudit, "nextjsRouter"), "Fixture audit must include nextjsRouter field");
```

## Improvement 2 — `--update` Version Display

**File:** `scripts/install.mjs`

**Problem:** When a user runs `node scripts/install.mjs --update`, they see `Repository updated` but no indication of what version they had before or what version they now have. They cannot tell if the update did anything.

**What to add:**

In the `updateRepo()` function, before running `git pull`, read the current version from `.codex-plugin/plugin.json`. After the pull succeeds, read the version again. Print both:

```js
function readPluginVersion() {
  try {
    const manifest = JSON.parse(
      readFileSync(join(root, ".codex-plugin", "plugin.json"), "utf8")
    );
    return manifest.version || "unknown";
  } catch {
    return "unknown";
  }
}
```

Usage in `updateRepo()`:
```js
const versionBefore = readPluginVersion();
// ... git pull ...
const versionAfter = readPluginVersion();
if (versionBefore !== versionAfter) {
  ok(`Updated ${versionBefore} → ${versionAfter}`);
} else {
  ok(`Already at latest (${versionAfter})`);
}
```

**No validator change needed** — this is output-only behavior.

## Improvement 3 — Environment Variable Name Extraction

**File:** `scripts/web-repo-audit.mjs`

**Problem:** The audit reports whether `.env.example` exists (`interestingFiles`) but does not extract the variable names inside it. Migration plans then say "environment variables exist" without listing them, so implementers have to open the file manually.

**What to add:**

After the `interestingFiles` array is built, read `.env.example` (or `.env.local` as fallback) and extract variable names:

```js
const envVarNames = [];
for (const envFile of [".env.example", ".env.local", ".env"]) {
  const envPath = join(root, envFile);
  if (!existsSync(envPath)) continue;
  try {
    const lines = readFileSync(envPath, "utf8").split("\n");
    for (const line of lines) {
      const trimmed = line.trim();
      if (!trimmed || trimmed.startsWith("#")) continue;
      const name = trimmed.split("=")[0].trim();
      if (name && /^[A-Z_][A-Z0-9_]*$/.test(name)) envVarNames.push(name);
    }
  } catch {
    // skip unreadable files
  }
  break; // use first env file found
}
```

Add `envVarNames` to the JSON output.

**Validator update:** add assertion:
```js
assert(Array.isArray(fixtureAudit.envVarNames), "Fixture audit must include envVarNames array");
```

Also add a `.env.example` file to `tests/fixtures/react-web/` with a few realistic variable names for the assertion to be meaningful:

```
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
VITE_API_BASE_URL=
```

## Improvement 5 — Navigation Type Detection in Mobile Audit

**File:** `scripts/mobile-app-audit.mjs`

**Problem:** The audit detects which navigation *libraries* are installed (e.g. `@react-navigation/native`, `expo-router`) but not what *type* of navigation the app uses. The completion plan cannot say "tab navigator with 3 screens" — it just says the library is present.

**What to add:**

After screen detection, scan source files for navigator usage:

```js
const navTypePatterns = [
  ["stack", /createStackNavigator|createNativeStackNavigator|Stack\.Navigator/g],
  ["tabs", /createBottomTabNavigator|createMaterialTopTabNavigator|Tabs\.Navigator|Tab\.Navigator/g],
  ["drawer", /createDrawerNavigator|Drawer\.Navigator/g],
  ["file-based", /expo-router|from ['"]expo-router['"]/g],
];

const navigationTypes = new Set();
for (const file of sourceFiles) {
  let text = "";
  try { text = readFileSync(file, "utf8"); } catch { continue; }
  for (const [type, pattern] of navTypePatterns) {
    if (pattern.test(text)) navigationTypes.add(type);
  }
}
```

Add `navigationTypes: [...navigationTypes]` to the JSON output.

**Validator update:** add assertion:
```js
assert(Array.isArray(mobileAudit.navigationTypes), "Mobile fixture audit must include navigationTypes array");
```

## Improvement 6 — Vue 2 vs Vue 3 Differentiation

**File:** `scripts/web-repo-audit.mjs`

**Problem:** The audit outputs `"Vue"` for any Vue project. Vue 2 (Options API) and Vue 3 (Composition API) have meaningfully different migration complexity — Vue 3 composables are closer to React hooks and port more cleanly.

**What to add:**

After the frameworks array is built, detect the Vue version:

```js
let vueVersion = null;
if (allDeps["vue"]) {
  const vueVer = allDeps["vue"];
  vueVersion = vueVer && (vueVer.startsWith("3") || vueVer.startsWith("^3") || vueVer.startsWith("~3"))
    ? "vue3"
    : vueVer && (vueVer.startsWith("2") || vueVer.startsWith("^2") || vueVer.startsWith("~2"))
      ? "vue2"
      : "unknown";
}
```

Add `vueVersion` to the JSON output (null for non-Vue projects).

**Validator update:** add assertion:
```js
assert(Object.prototype.hasOwnProperty.call(fixtureAudit, "vueVersion"), "Fixture audit must include vueVersion field");
```
